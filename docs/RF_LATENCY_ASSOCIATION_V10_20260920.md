## 已确认的代码缺陷及修复

### 第一帧 SPI 身份被最新状态覆盖

STM32 用事件第一帧成功 SPI 的 seq 关联四个源阶段。TX 的 SPI 字节解析器原来只保留最新输入，等 RF 定时器读取该输入时才创建测量事件。若一次解析收到 seq=9、10、11 的同一事件，RF 只看到 11，随后源 sidecar 携带的 9 就会被 `RF_SPI_WriteTrace` 拒绝。三个重复 sidecar 都携带 9，重复发送无法解决这个身份错误。

修复：测量开启时，在 SPI 输入完成协议校验、尚未被后续输入覆盖之前，建立事件记录，并与最新输入的发布放在同一短临界区。RF 定时器继续发送最新完整状态；同一事件的后续 SPI 帧不覆盖事件第一帧身份。测量关闭时不调用此额外采集路径。

同时在第一帧消费时保存对应 NSS 结束时间。sidecar 延后处理不再依赖一个可能已经超出 8 ms 查询期限或被 SPI seq 回绕覆盖的端口缓存。若解析早于 NSS IRQ，则允许在 sidecar 到来时补查；没有有效物理结束时间仍不生成有效 TX 耗时。

### SPI RX DMA 重启后 NSS 起点失效

SPI 读事件结束和溢出恢复会把 RX DMA 重置到 ring offset 0，但 NSS 测量原来保留重置前的 offset。下个输入的捕获会从旧位置检查帧头，丢失对应 SPI 结束时间。

修复：DMA 重启同步重置 NSS 起点；SPI 正在输出事件时不捕获为输入；其他 GPIO 唤醒标志也不能在测量开启时关闭整个 GPIO A IRQ。

### 状态和显示

RX build ID 改为 `0x1910`。不改变空口协议 v2 或 5/7 B 输入格式：RLT2 flags bit5 表示收到了候选源记录；只有完整 RF 发送序号准确匹配后才展示源阶段并允许总耗时。

* `Source record missing`：尚无可用的候选源记录。
* `TX attempt mismatch`：候选记录已到，但没有对应的有效发送尝试。
* `Invalid/expired record`：记录被失效、过期或序号不确定等条件拒绝。
* 部分记录表头显示 partial samples，不再把缺失记录解释为未开启开关。
* 失败原因保持单行省略并可悬停查看，避免原截图中的跨行重叠。

仍然不根据同一键值猜测配对、不放宽到错误 RF seq，不把 RF≈模型段改称实测，不新增独立 RF 诊断时隙。

## 交付与实机验收

归档 `.hbox/rf-latency-v10-20260920/` 保存 TX/RX 匹配镜像、哈希和说明。若已刷 v9 STM32，本轮只需更新 TX、RX，并重新启动新监视器。

TX 必须使用既有 `python tools/hbox.py flash tx` 普通无锁入口，保留 0x0000–0x0FFF IAP；RX 由用户沿用之前流程自行更新 `RX.hex`。未修改任何保护、锁定配置或冻结烧录脚本。

验收时确认 RX 0x1910，启用 HID/Latency，清空旧记录，间隔约半秒单独按下/松开几个键。检查源四阶段、TX 阶段能否补齐及完整率，再检查快速交替、释放、单边重启；即使有完整总和，也仍是 sampling → USB IN complete 的带 RF 边界估算结果。旧记录不能在新会话里补算。
