# 持续监测闪退排查（2026-09-19）

用户现象：持续监测时应用直接退出。

## 已取得的证据

- Windows Application 日志：2026-09-17 20:59:34，仓库内 Electron 33.4.11
  出现 `0xc0000409` 原生崩溃；20:59:36 WER 记录 `BEX64`。
- 同日 23:10:26，WER 记录 Electron 的 `RADAR_PRE_LEAK_64` 预警。
  预警和异常代码不足以定位具体分配点，也不能证明两次事件同因。
- Renderer 聚合器里的事件、图表和延迟数组已有数量上限。
  未发现这些数组持续保留整段历史。
- 主进程向 Renderer，以及 Worker 向 Renderer 发送消息原先没有消费确认。
  接收端长时间停顿时，即使业务数组有上限，IPC 队列仍可能持续增长。
- 历史查询原先整文件读取并拆行；日志越大，查询时的内存峰值越大。
  这不是持续监测闪退的直接证据，因为该路径需要触发历史查询。
- 历史追加写盘异常原先可能逃逸到采集回调，导致监测中断或进程退出。

## 本次改动

- 每个实时 IPC 消费者最多一批待确认消息，每批最多 500 条，待发送最多 2000 条。
  拥堵时保留较新数据并统计丢弃数量；正常写盘的 monitor 历史仍独立保留。
  串口显示队列丢弃的数据不会进入 Renderer IndexedDB。
- IPC 确认等待 Worker 处理或串口数据库写入；Worker 完整快照同样等待消费确认。
- 延迟子窗口仅接收延迟事件；关闭窗口时显式关闭子 WebContents。
- 历史查询使用 64 KiB 反向分块读取，限制查询条数及损坏长行的缓冲长度。
- 写盘失败保留错误状态并继续实时监测，不把磁盘错误误判成设备掉线。
- 加入有轮换上限的 `runtime-diagnostics.jsonl`：每 30 秒记录进程内存、
  队列数量和丢弃计数，记录 Renderer/子进程退出原因和未捕获 JS 异常。

## 验证及限制

- TypeScript 类型检查、Electron 编译、Renderer 生产构建通过。
- 40 项 Node 自动测试通过，包括 10 万条事件下的阻塞恢复、Worker 快照积压、
  preload 异步消费确认、写盘失败恢复、UTF-8 跨块读取和损坏长行。
- 约 64 MiB JSONL 文件在 32 MiB V8 堆限制下成功分页查询。
- 独立 Electron 集成测试在加载测试页面时超时，未进入持续数据阶段；
  GPU 禁用和独立隐藏启动也未完成页面加载。不能将此测试记为通过，
  也没有完成真实设备数小时连续运行验收。
- 尚未取得用户闪退当时的 JS 堆或原生堆栈，不能宣称已确认唯一根因。
  新日志用于在再次发生时区分消息积压、内存增长、磁盘错误与原生崩溃。

改动需要关闭旧进程、重新运行构建后的应用才生效；已安装的旧 exe 不会自动更新。
本次没有操作设备固件、烧录流程或芯片保护状态。
