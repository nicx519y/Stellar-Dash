# XORA 整机固件安装（协议 2）

## 升级流程

下载 → 解压与校验 → 浏览器备份配置 → 设备备份当前 TX → 写入主控备用槽 → 暂存新 TX → 离线安装 TX → 切换主控 → 重连核验。

升级浮层把上述事务合并为三个用户可见阶段：**下载和校验 → 备份固件和配置 → 安装升级**。阶段文案在进度数字下方横向切换，两侧淡出；安装升级包含主控/TX 暂存、离线安装、切换和重连核验。异常、自动恢复和最终结果仍单独提示；浮层位于页面中上方，正常屏幕保留更高的进度区域并随内容增长，较矮屏幕收紧留白并缩小进度环，正文无内部滚动条。

下载使用 `cache: no-store`，本地服务传输和浏览器内解压、验签、摘要校验可很快完成，不人为延时。TX 备份仍读取完整的 444 KiB Application 区域两遍，并擦除备份区、写入及回读 Flash、核对身份；444 KiB 是区域容量，不是实际固件长度。

支持新版读回能力的主控/TX 使用现有 15 MHz SPI 大块 DMA 通道：每份 1024 字节消息携带 992 字节固件数据，两遍共 918 次读取（旧方式为 18,944 次）。每块受高速链路 CRC、epoch、顺序和队列信用保护，并核对请求 ID、偏移、长度及返回状态。备份消息只在 SPI 内部流转，USB 入口拒绝这类消息，TX/主控接收端也不会将其转发到浏览器。每次主循环只推进一块，最多等待 100 毫秒；失败、损坏或超时不提交有效备份，不开始写新 TX。

大块能力通过独立的 `TX_IMAGE_BULK_INFO` 查询协商，不改变整机协议 2、Flash 布局或历史备份格式。旧 TX 明确返回 `UNSUPPORTED` 时，主控使用原 48 字节控制帧；查询超时、异常响应及已协商大块通道的传输失败不会降级重读。因此从旧 TX 首次升级到新主控/TX 时仍可能较慢，完成后后续升级才能使用 DMA 读回。该优化只减少传输往返，Flash 擦写和两遍校验的耗时仍存在；实际加速与并行状态查询需实机验收。

WebConfig 保留一个升级界面，用一个进度环显示整个流程：下载 0–10%、解压校验 10–15%、配置备份 15–20%、TX 备份 20–40%、主控暂存 40–70%、TX 暂存 70–80%、离线安装 TX 80–90%、切换主控 90–95%、重连核验 95–100%。这些是流程权重，不代表耗时比例。主控 Application 与 ADC 数据按累计字节计算；切换组件不重置。离线安装的显示值从 80% 按约一分钟的预期耗时推进，渐近 98%；设备里程碑可以推进显示值，只有匹配事务且整机版本核验成功才显示 100%。估算只用于界面，不写入设备进度、持久化任务或完成结果；失败、恢复和超时冻结当前显示值。激活前持久化事务 ID、签名声明摘要、目标版本、首次激活时间及真实进度；刷新后使用首次激活时间恢复估算，不重新计时。状态必须匹配事务 ID、目标摘要和版本。

80% 表示组件暂存传输完成；随后准备和激活请求仍会完整复核声明签名、TX 备份及主控/TX 镜像摘要，激活记录提交后等待 500 毫秒再请求重启。整机安装器的 Flash 摘要读取按每份镜像退出一次 QSPI 映射、连续间接读取并计算 SHA-256、最后恢复原映射模式；避免原先每 512 字节触发一次 Flash 复位及 5 毫秒等待。读取、模式切换失败和摘要不匹配均拒绝通过；所有校验及重启后的重新复核保留。优化影响准备、激活、启动核验和恢复复核，需要先更新主控才能作用于下一次由它发起的安装。固定等待节省可由读取块数计算，实际总耗时需实机测量。

离线每 3 秒尝试重连已授权设备，连接后每 2 秒查询状态，同一观察器最多一个连接或状态请求。正常安装期间隐藏手动重连按钮，提示保持供电，不拔 USB、不关机。首次激活请求起 180 秒无终态，显示“TX 升级失败（连接超时）”，停止周期重试并保留任务和手动重连入口；超时或异常后可通过该入口重新授权设备。网页不会因此发送取消、重刷或恢复命令。之后匹配的设备真实结果可以替换网页超时状态。

成功完成后清理浏览器中的续接任务，仅在本次打开的进度弹窗保留完成结果；关闭弹窗或重新进入固件页后不再显示上次 100% 进度。旧版遗留的 `completed` 记录也会清理。未完成、超时及恢复异常任务继续保留，可重连查询；设备事务日志不受浏览器任务清理影响。

### 实际 TX 刷写协议

主控在 IAP 协商成功后、发送擦写 `BEGIN` 前，将实际协议持久化到本次事务；记录提交失败时不开始擦写。`get_firmware_inventory` 和 `get_release_install_status` 返回 `txInstallMode` 与 `txRecoveryMode`，取值为 `dma`、`small-packet` 或 `unknown`。安装和恢复独立记录，恢复重试前清除本次恢复协议，保留原安装协议。

WebConfig 重连并匹配事务 ID、目标摘要和版本后，记录实际安装协议。升级浮层不展示安装协议文案；恢复发生时仍显示恢复协议。设备详情保留上次记录，可在关闭完成浮层后查看。DMA 每包固件数据 1000 字节，小包每包 40 字节；这表示离线 IAP 实际协商结果，与 TX Application 的备份 DMA 能力不同。离线 USB 断开期间无法实时取得新结果，不根据 Application 版本推测 IAP。超时、协商异常及旧日志缺少字段时显示未知。

事务日志保留原 v2 标识和完整有效前缀，新增字段使用扩展 CRC 和提交标记；扩展写入和回读后，最后发布旧前缀的提交标记，旧主控仍可继续完成升级或降级事务。旧记录及旧主控后续提交的记录按协议未知读取，备份和恢复字段继续有效。该功能需要更新主控与托管 WebConfig，TX Application/IAP 不必因上报功能重刷；从不具备记录功能的旧主控发起的首次升级仍可能显示未知。

新版流程没有实体按键授权或按键重试入口。

### 断开与断电

- 下载、校验、配置备份只操作浏览器，尚未写设备。激活前断开 USB 会中断传输；原主控和 TX 仍保留。TX 备份中断重启后重新备份，主控/TX 暂存接收进度不能跨重启续传，应取消未激活事务后重新开始。
- 激活后安装和恢复由设备独立执行。断开 USB 数据但保持设备供电，不会取消刷写；网页继续等候同一事务。USB 同时供电时，拔线按断电处理。
- 新 TX 写入前已持久化安装次数。写入阶段断电后，主控能启动时会进入旧 TX 恢复；恢复次数同样跨断电保留，最多两次。已提交 TX 验证阶段后重启会再次核验，再决定切换主控或恢复。metadata 提交中断、主控不能执行及真实 Flash 故障仍可能需要维护恢复，不能承诺任意断电都能自动恢复。
- 安装结果和当前连接状态独立显示。完成后断开连接，在尚未关闭的本次进度弹窗保留结果及 100%，同时明确提示设备断开；不能把断开改报成本次升级失败。
- WebHID 拔插事件立即更新连接状态。USB 仍枚举但主控退出 WebConfig 时，以现有只读时钟命令每 3 秒检查会话，单次请求超时 2 秒；走共享命令队列，不启用 RF 或按键采样。升级、配置独占、初始化和后台页面暂停检查。网页主动退出 WebConfig 收到应答后直接结束会话；安装期间的预期断连继续由升级观察器处理。

## 基线与发布包

- 日常主控烧录 `python tools/hbox.py flash app A --build`（B 槽改为 B）使用与 `https://manager.st-dash.com` 匹配的正式签名密钥，保持 `unlocked-development`。构建前核对公开验签公钥，密钥缺失、不匹配或服务器不可达时停止，不回退到开发密钥。产物与公钥位于独立的 `.hbox/webconfig-formal/`，正式私钥仍留在部署配置指定的外部路径；本地实验室 PKI 不被替换。不带 `--build` 时只使用该目录已验证且匹配所选槽位和线上公钥的产物。
- 仅准备上述产物、不访问硬件：`python tools/formal_application_build.py --slot A`。该入口复用完整构建契约，会编译 bootloader、主控和 TX，但主控烧录仍沿原 `webconfig_flash.py --simple-execute` 事务执行；未改变写入范围、目标检查、回读和 metadata 最后提交。迁移前必须处理旧状态目录中的未完成烧录事务。此次分发变更及冻结契约原有差异仍待实机烧录、启动和线上升级验收，不更新冻结哈希。
- 主控、TX 和目标发布包必须支持安装及维护协议 2。旧协议发布包保留目录浏览，不能在新版网页安装。
- 首次迁移通过既有维护入口更新主控/TX Application；不更新 bootloader 或 IAP 来建立基线。本实现不自动烧录或发布，也不替换已发布 1.0.1。
- 使用 `python tools/prepare_release_identity.py --version <组件版本>` 生成构建身份，再编译两个主控槽和 TX，随后使用本地固件草稿命令打包。不能在两槽构建之间重新生成身份头。
- 主控 metadata 必须明确声明 `webresources_optional=1`，`webresources` 为 inactive 且 size=0；所有签名、摘要、地址、硬件、安全版本和无锁构建门禁继续保留。
- 配置版本仍要求精确兼容，不自动迁移或恢复默认。浏览器配置备份必须成功才能开始设备写入。
- 更新说明可以从 Git 自动生成，管理员预览、编辑后人工发布；不再以验收记录字段作为发布门槛。实机验收仍是交付必需证据。

## TX 读回与备份

维护协议提供 `TX_IMAGE_INFO` 和 `TX_IMAGE_READ`；分块读取只允许 Application `0x1000–0x6FFFF`，每次最多 48 字节，不可访问前 4 KiB IAP、配置字或保护区域。

备份位于目标备用槽 `webresources` 起始处的 512 KiB，与 `0x90790000` 新 TX 暂存区独立。前 64 KiB 保留备份头，正文为完整 `0x6F000` 字节 Application。主循环分块读取并写入，第二遍重新读取 TX 计算 SHA-256，再与备份 Flash 回读摘要比较，同时检查前后 TX 版本、构建和维护身份一致。

备份头绑定事务 ID、源/目标槽、TX 身份、长度和 SHA-256；正文和头回读成功后最后写提交标记。仅有效备份允许接收目标组件和激活。备份中断重启时从头重新读回；组件暂存进度丢失时取消未激活事务后重新开始。

## 自动恢复

新 TX 完整安装最多一次，保留既有 SPI IAP 包级重试。写入、启动、维护能力或身份校验失败后，先验证备份和源主控镜像，再恢复旧 TX Application。恢复最多两次，每次写入前提交尝试次数；断电不清零次数。

每次 Application 启动核验允许两次完整维护会话。若 CAPS/身份读取失败或应答释放故障锁住会话，先关闭旧会话，再普通重启 TX 进行一次只读核验；不会重发 IAP 擦写，也不重置安装/恢复次数。持续失败仍进入原来的恢复或终态错误路径。日志中的安装/恢复错误包含 IAP stage、client/device status 和 offset，便于区分写入与启动核验失败。

恢复成功先确保源主控签名 metadata 正确并回读，重启核验旧主控/TX 身份，提交 `restored`：升级失败，已恢复原版本；随后允许正常运行和 USB。

备份无效时提交 `restore-failed / TX_BACKUP_INVALID`；恢复写入或启动失败提交 `restore-failed / TX_RESTORE_FAILED`。屏幕持续显示缺少恢复镜像或需要维护恢复及错误码，按键不会关闭或触发再次刷写。设备现有字体为 ASCII，因此屏幕使用英文原因；网页同步提供中英文文案。事务记录保留原始升级错误、恢复错误、恢复阶段和次数。旧日志兼容读取；旧失败记录没有备份时报告 `LEGACY_NO_BACKUP`，不清空记录或伪造成功。

日志仍采用 metadata 分区的两个 24 KiB bank `0x90574000`、`0x9057A000`；新版保留旧记录前缀，扩展记录采用独立 CRC 和最后提交标记。原 metadata 的 807 字节结构和冻结烧录入口不变。

## 验证与限制

### 离线 TX 大块 DMA 刷写

主控先通过原有 64 字节 IAP v1 帧发送 `DMA`（命令 7）：`offset=1024`、
`value=0x32414D44`、空 payload。新 IAP 返回匹配序号的 v1 成功应答并先准备
RX DMA，再释放 ready 信号。主控随后启用 7.5 MHz SPI4 DMA；所有请求使用
IAP v2 的 1024 字节帧（20 字节头、1000 字节数据、4 字节 CRC32）。这个版本号
属于 IAP 传输协议，与整机安装/维护协议 2 分别协商。

- 只有有效应答明确返回 `BAD_COMMAND` 才继续使用旧 IAP 的 40 字节小包。
  超时、应答损坏、版本/序号错误或 DMA 初始化失败均在 BEGIN 擦除前终止。
- 旧主控/维护工具仍可使用新 IAP 的原有 v1 小包；收到有效协商后，本次启动
  的 IAP 只接受 v2 帧。重新上电回到 v1 协商入口。
- 新模式用 CH585 SPI0 RX DMA 收整帧，NSS 结束、完整长度、无 FIFO 溢出、
  版本/保留字段/CRC 全部有效才处理命令。短帧、长帧及溢出不触发 Flash 写入，
  溢出期间不在帧中途重新接收。STM32 复用 D2 SRAM 缓冲、缓存维护和双 DMA
  完成处理；8 字节 ACK 仍由预装满的 FIFO 发送/读取。
- 写入范围仍限定 `0x1000–0x6FFFF`。数据块先写入再回读校验；确认丢失时，
  重发已提交的数据须与 Flash 相同才能应答成功，不再把 DMA 的 BAD_ADDRESS
  当作可能成功。整幅 CRC 校验及 VALID metadata 最后提交保持不变。
- 新镜像安装和旧 TX 备份恢复共用这一路径，整机安装一次、恢复最多两次的
  持久化预算不变。升级成功仍须通过 Application 启动与版本/身份核验。

IAP 的官方 4 KiB 地址布局保持不变。为容纳 DMA 接收，TX Makefile 给 IAP
及其独立 SDK/board 对象启用 LTO，Application/RF 的对象和编译选项不变；
该构建流程变化需要重新验收，未修改冻结契约哈希。当前工具链链接结果约
3.9 KiB，不以编译成功替代实机 DMA、恢复和断电验收。

**启用条件：主控和设备内的 IAP 均包含此实现。** 更新 TX Application 或通过
WebConfig 发布包升级不会更新 IAP。现有旧 IAP 继续使用小包，因此仅重新打包
普通发布包不能启用离线 DMA。本任务没有烧录 IAP。用户于 2026-10-04 明确
解除仅 TX IAP 前 4 KiB 的写入禁令，允许独立维护更新；保护位、锁定状态、
芯片配置字及相邻 Application 的写入边界仍须遵守根目录规则。现已提供独立
WCH-Link RAM 维护入口，默认只检查产物，详见 [TX IAP 维护](tx-iap-maintenance.md)。
该入口尚待实机安装和启动验收；该授权不改变 WebConfig 和普通 TX 更新的写入范围。

### 恢复与断电验收

先通过独立 Mock 检查页面故障反馈。在 `application/www` 执行 `npm run dev:mock`，打开 `http://127.0.0.1:4000`，在安装前用浏览器控制台设置：

```javascript
sessionStorage.setItem('xora-mock-install-failure', 'tx');
```

| 值 | 检查结果 |
|---|---|
| `backup` | 备份失败，阻止新 TX 写入 |
| `tx` | TX 启动失败，显示已恢复原版本，源主控槽保持一致 |
| `restore` | 显示恢复失败及维护错误码，无再次刷写按钮 |
| `missing-backup` | 显示无有效恢复镜像 |
| `timeout` | 离线等待达到 180 秒后显示连接超时 |

每个场景在新预览会话中开始；测试后 `sessionStorage.removeItem('xora-mock-install-failure')` 清除故障。Mock 不访问硬件，不能替代以下实机验收：

1. 使用专用、已验签的受控故障 TX 包分别触发写入失败和启动失败，确认自动恢复旧 TX、源主控 metadata 和正常 USB；普通 1.0.2 包没有故意损坏 TX，不能用它证明故障恢复。
2. 在备份提交、主控暂存、新 TX 安装、metadata 切换及恢复提交各阶段分别测试一次断电重启。核对旧/新身份、事务阶段、原始错误及持久化恢复次数，不允许无限刷写；没有有效备份不能安装新 TX。
3. 无备份/备份损坏和两次恢复失败路径须在受控故障台验收。屏幕持续显示原因及错误码，不自动消失，没有 GPIO1+FN 操作。终态失败保留记录，停止升级重试并使用既有无锁维护入口。
4. 全部路径确认 CH585 写入仅在 Application，IAP 前 4 KiB及所有芯片保护/锁定状态保持不变。RF 自动回归与设备采样继续暂停。
