## 最有区分力的证据：未发送的 TX 测量槽

RHP2 `rfTraceOverwrites` 从 897 增加到 958，增量 61。它来自 TX 的 `g_relative_overflow`，只在未发送槽被复用，或待发送记录超过一秒被丢弃时增加；不是 RX 收不到无线分片的计数。

TX 使用非零 6-bit tag，共 63 个测量槽。182 条中的前 119 条，恰好有 61 条 `Source record missing`；这些是后续 63 条覆盖窗口之外的旧记录。最终覆盖计数增量也恰好为 61。初始约十秒的按键停顿期间计数没有增加，后续 tag 复用后才开始增加。

这个对应关系强烈支持：大量源记录在 TX 端没有达到成功发出的状态，而后随着 tag 复用被覆盖。不能解释为全部源记录已发送，只是在 RF 空口或桌面渲染中丢失。计数没有携带 event ID，因此仍不能把每次覆盖与每一行逐一做实测配对，也不能将 61 直接当作全部 103 条的唯一归因。

## ADC 到 TX 为什么会一起为空

普通 5/7-byte DATA 包携带完整按键状态，但不携带 ADC、Logic、SPI wait、SPI、TX 五段耗时。

STM32 在首次成功发送该状态后生成四个源阶段，再以 SPI `0x09` sidecar 重复三次发送给 TX。TX 将源阶段、SPI 结束时间和最多六次 RF 发送尝试组成一份 TRACE；RX 收到完整 TRACE 后才按 RF 序号关联到该状态变化。

`connect-monitor/electron/sources/relative-latency.ts:41–49` 按 RX 的 flags 展示：源阶段无效时前四列为空，TX 有效位不存在时第五列为空；USB 已完成且没有候选源记录位时显示 `Source record missing`。这不是面板分别漏算了五个值。

## 当前代码仍存在的源记录拒收路径

1. `application/Cpp_Core/Src/rf_transport.cpp:546–555` 将首次成功 SPI 的 `payload[0]` 固定为源记录 `spiSeq`，三次副本使用同一身份。
2. `RF_PHY_Hop/TX/APP/RF_PHY.c:2984–2993` 在第一次接纳某个 tag 时，把当时输入帧序号固定为 `r->spi`。
3. `RF_PHY_Hop/TX/APP/RF_PHY.c:2470–2489` 只有 tag 和该 SPI 序号同时相等，才设置 `r->source=1`；失败只设置一个累计诊断位，不保留待匹配源记录。
4. `RF_PHY_Hop/TX/APP/rfm_spi_port_ch585.c:394–405` 主循环遇到被 NSS 快速路径越过的旧输入帧会直接跳过；它不会为旧首帧补回测量身份。
5. NSS 快速路径 `rfm_spi_port_ch585.c:831–854` 只接受两次 ISR 观察位置之间正好 14 或 38 字节的事务。如果中断延后、多个事务合并，或首帧未通过该捕获路径，后续输入可能先建立事件槽。

因此存在如下确定的代码失效路径：STM32 成功发出首帧 seq=N；TX 首帧捕获未完成，后续 seq=N+1 先建立同一 tag 的槽；主循环跳过旧 N；三次源记录都携带 N，全部被 `r->spi == payload[0]` 拒绝。输入状态仍正常更新，源测量却永久缺失。重复三次不能修复身份不一致。

这条路径在代码中成立，且与本次 TX 未发送槽增长一致；现有日志未上报逐事件 SPI 首帧、源记录拒收原因及 DMA 覆盖计数，尚不能证明它解释了本次每一条缺失。另一个需要区分的上游断点是 SPI DMA：输入由 NSS 发布，sidecar 只由主循环解析；1024-byte DMA 环被覆盖时，主循环会丢弃积压字节，因此也可能只保住输入、丢掉源记录。

## 为什么缺失会一直留着

`short_prepare_trace()` 在 `RF_PHY.c:3012` 先跳过 `source==0` 或 `count==0` 的槽，之后才在 3031 行判断一秒过期。所以没有源记录的槽不会走这处一秒清理，而是等 tag 复用才增加覆盖计数。

RX `short_send_trace()` 在 USB 完成位已经置位后，也不会把仍缺源的行改为超时。因此面板可以长时间显示 `Source record missing`。等待更久不会让已被 TX 覆盖的源记录恢复。

## 次要的独立限制

- TRACE 的 54-byte payload 加头和 CRC 共 64 bytes；每个 RF 附带分片仅承载 1 byte 记录内容，共发送三轮。没有整条 TRACE 的接收确认或缺片补发；三轮后 TX 停止，RX 缺任一必要分片就不交付。这可能产生额外缺失，但不能单独解释 TX 未发送槽的增长。
- 只记录前六次 RF 尝试；RX 使用的包不在其中时显示 `TX attempt mismatch`。本次最终只有 1 条属于该类别，不支持它是主要原因。
- RX 新输入快照合并也可能改变被记录的首个 RF 序号；不能通过按键值猜配或取消序号校验来掩盖这一限制。

## 修复方向

优先修复 TX 源记录归档与首帧身份的生命周期：最新按键快照可以合并，但源事件身份必须独立保留；旧输入不能重新发布为当前状态，但其经过校验的测量元数据应允许补档。任何补档都必须保留实际 SPI 边界和 RF 尝试的准确归属，不能直接拿后续帧时间替代首帧时间。

同时需要按原因增加少量累计计数：源 sidecar 收到、SPI 身份拒收、DMA 积压丢弃、缺源槽复用、已归档 TRACE 发出、RX 重组不全及候选超时。这样才能把本次尚无法区分的几个断点实测分开。随后再处理 TRACE 分片可靠性；只增加 UI 等待时间或盲目增加三轮重复次数不会修复首帧身份不一致。
