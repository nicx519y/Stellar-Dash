# RF24G 8K 12B Baseline

Date: 2026-05-18

This document records the current baseline for continued RF24G tuning. It describes the implemented data path from STM32 SPI output, to `RF_PHY_Hop/TX`, to `RF_PHY_Hop/RX`, including payload size, trigger rate, transfer bandwidth, and the diagnostic fields that should be used as the reference for later changes.

## Baseline Goal

The current target is a stable low-latency wireless input path:

```text
STM32 application -> SPI INPUT_DATA -> CH58x TX -> 2.4G RF -> CH58x RX
```

Current accepted baseline:

- Trigger rate: `8000 Hz`
- STM32 SPI command payload: `12 B`
- STM32 SPI frame size: `16 B`
- RF air payload: `12 B`
- RF channel: fixed channel `16`
- Frequency hopping: disabled
- RF sequence byte: air payload byte `0`
- Payload data bytes: air payload bytes `1..11`
- Latest-sample policy: TX always sends the latest completed SPI DMA half-buffer available at the 8K RF timer tick.

Representative current result:

```text
[R5]d5000 o39637 f47 h7927 g369 c44 t3 a3 m11
[R5]d5000 o39567 f46 h7913 g440 c42 t4 a3 m4
```

This is roughly `7.9K/s` effective RX good packets with low CRC failure for the current 12B RF payload.

## Current Parameters

### STM32 Application

File:

- `application/Cpp_Core/Src/rf_transport.cpp`

Parameters:

- `INPUT_PAYLOAD_LEN = 12`
- Command: `CMD_INPUT_DATA = 0x06`
- SPI frame format:

```text
0xA5, 0x06, 0x0C, payload[12], checksum8
```

Frame size:

```text
3 header bytes + 12 payload bytes + 1 checksum byte = 16 bytes
```

Nominal bandwidth at 8K:

```text
16 B/frame * 8000 frame/s = 128000 B/s = 1.024 Mbit/s raw SPI payload stream
```

Payload layout generated by `RFTransport::sendInput()`:

```text
payload[0]  = seq low byte
payload[1]  = buttons low byte
payload[2]  = buttons high byte
payload[3]  = dpad encoded value
payload[4]  = LT
payload[5]  = RT
payload[6]  = LX low byte
payload[7]  = LX high byte
payload[8]  = LY low byte
payload[9]  = LY high byte
payload[10] = RX low byte
payload[11] = RX high byte
```

The current 12B format intentionally drops the remaining fields from the older 15B gamepad payload. For the present wireless-air test, this is acceptable and keeps the 8K link easier to stabilize.

### TX SPI Receive

Files:

- `RF_PHY_Hop/TX/APP/include/rfm_config.h`
- `RF_PHY_Hop/TX/APP/rfm_spi_port_ch585.c`
- `RF_PHY_Hop/TX/APP/RF_PHY.c`

Parameters:

- `RFM_RF_INPUT_PAYLOAD_LEN = 12`
- `SPI_RX_FRAME_BYTES = 3 + 12 + 1 = 16`
- `SPI_RX_DMA_RING_SIZE = SPI_RX_FRAME_BYTES * 2 = 32`

Implementation:

- SPI0 is configured as slave RX DMA loop.
- DMA buffer is exactly two fixed frames:

```text
half 0: byte 0..15
half 1: byte 16..31
```

- The STM32 continuously writes fixed 16B command frames.
- TX does not wait for a software parser/poll path in the 8K RF hot path.
- At each 8K RF timer interrupt, TX calls `rfm_spi_port_peek_latest_input()`.
- The peek logic reads the DMA write pointer and selects the just-completed half:

```text
if write_pos < 16: latest completed half is 16..31
else:              latest completed half is 0..15
```

- Header validation checks only:

```text
byte[0] == 0xA5
byte[1] == 0x06
byte[2] == 12
```

- The checksum is intentionally not verified in the 8K timer path. Earlier checksum/scan work inside the high-rate path increased RF disturbance; removing it brought RX back to about `7.9K/s`.
- SPI DMA end interrupts are not used as the data cadence. FIFO overflow interrupt remains enabled for diagnostics/recovery.

### TX RF Send

File:

- `RF_PHY_Hop/TX/APP/RF_PHY.c`

Parameters:

- `RF_TEST_FREQUENCY = 16`
- `RF_TEST_ENABLE_HOP = 0`
- `RF_TEST_DATA_LEN = 12`
- `RF_REPORT_PPS = 8000`
- `RF_TX_USE_TMR0_IRQ = 1`
- `RF_USE_LOW_LEVEL_BASIC = 0`
- `RF_LINK_ACCESS_ADDRESS = 0x71764129`
- `RF_LINK_CRC_INIT = 0x555555`
- `RF PHY = LLE_MODE_PHY_2M`
- `RF_TX_SEND_TIME = 40`

Implementation:

- Timer0 is configured as the RF send cadence:

```text
g_tick_per_evt = GetSysClock() / 8000
TMR0_TimerInit(g_tick_per_evt)
```

- `TMR0_IRQHandler()` is the 8K send trigger.
- Each Timer0 interrupt:

```text
rf_fill_payload()
RFIP_SetTxStart()
RFIP_SetTxParm(&gTxParam)
```

- The RF air frame uses the WCH RFIP DMA layout:

```text
TxBuf[0] = 0x55
TxBuf[1] = 12
TxBuf[2..13] = RF air payload[12]
```

- Current air payload layout:

```text
air[0]    = TX-generated RF sequence
air[1..11] = latest SPI payload[1..11]
```

Note: STM32 payload byte `0` is consumed only as an SPI-side sequence/source indicator. The actual RF sequence is generated by TX and placed at air byte `0`, so RX gap statistics reflect actual RF transmit order.

Air payload bandwidth at 8K:

```text
12 B/frame * 8000 frame/s = 96000 B/s = 768 kbit/s air payload bytes
```

### RX RF Receive

File:

- `RF_PHY_Hop/RX/APP/RF_PHY.c`

Parameters:

- `RF_TEST_FREQUENCY = 16`
- `RF_TEST_ENABLE_HOP = 0`
- `RF_TEST_DATA_LEN = 12`
- `RF_TEST_ENABLE_RF_RX = 1`
- `RF_RX_RESTART_IN_CALLBACK = 1`
- `RF_RX_TIMEOUT_HALF_US = 10000`
- `RF_LINK_ACCESS_ADDRESS = 0x71764129`
- `RF_LINK_CRC_INIT = 0x555555`
- `RF PHY = LLE_MODE_PHY_2M`

Implementation:

- RX uses RFIP receive through `RFIP_SetRx(&gRxParam)`.
- RX restarts inside the RF callback when `RF_RX_RESTART_IN_CALLBACK == 1`.
- This keeps measured restart cost low, usually around:

```text
a ~= 3 us
m ~= 4 us
```

- RX validates:

```text
RxBuf[1] == 12
seq = RxBuf[2 + 0]
```

- RX gap count is based on the RF sequence byte in air payload byte `0`.

## Diagnostic Logs

### STM32 Logs

Useful STM32 reference logs:

```text
[REPORT_SCHED][5s] irq:40000 consumed:39618 dropped:382 pending:0 irq_hz:8000 consumed_hz:7923 rate:8000
[RF_SEND][5s] calls:39618 ok:39618 fail:0 hz:7923 total:... rate:8000
[RF_BRIDGE][5s] tx:39618 ok:39618 fail:0 input:39618 input_ok:39618 input_fail:0 input_hz:7923 ... txLen:16
```

Expected meaning:

- `irq_hz`: TIM2 scheduler interrupt rate. Target `8000`.
- `consumed_hz`: application consumption rate. Current normal value is about `7920`.
- `txLen`: SPI frame length. For this baseline it must be `16`.
- `input_hz`: accepted `INPUT_DATA` send rate, usually about `7920`.

### TX Logs

Current TX log format:

```text
[TX][win] len:%u dt:%lums irq:%lu sent:%lu upd_hz:%lu peek:%lu/%lu peek_hz:%lu sf:%lu pf:%lu rb:%lu ch:%u txret:%u
```

Field meanings:

- `len`: RF air payload length. Baseline must be `12`.
- `dt`: actual statistics window in ms.
- `irq`: Timer0 ISR count in the window. Target about `40000 / 5s`.
- `sent`: RF send attempts scheduled by Timer0. Target about `40000 / 5s`.
- `upd_hz`: payload update/send trigger rate. Target about `8000`.
- `peek:ok/miss`: DMA double-buffer latest-frame acquisition count.
- `peek_hz`: successful DMA peek rate. Target about `8000`.
- `sf`: `RFIP_SetTxStart()` failure count. Target `0`.
- `pf`: `RFIP_SetTxParm()` failure count. Target `0`.
- `rb`: sequence rollback count after RF start/param failure. Target `0`.
- `ch`: current RF channel. Baseline fixed value `16`.
- `txret`: legacy low-level TX return field. It is not the primary health metric in the current RFIP path.

Expected baseline example:

```text
[TX][win] len:12 dt:5020ms irq:40012 sent:40012 upd_hz:7970 peek:40170/0 peek_hz:8003 sf:0 pf:0 rb:0 ch:16 txret:255
```

Old `[SPI][win] raw/frame/...` logs are not the baseline health signal for this version. The high-rate path now uses direct DMA half-buffer peek from the 8K Timer0 ISR.

### RX Logs

Current compact RX log format:

```text
[R5]d%lu o%lu f%lu h%lu g%lu c%lu t%lu a%lu m%lu
```

Field meanings:

- `d`: statistics window in ms.
- `o`: RF packets accepted as valid.
- `f`: RF failures in this window.
- `h`: valid RX packet rate, `o * 1000 / d`.
- `g`: RF sequence gap count.
- `c`: RF CRC error count.
- `t`: RF timeout count.
- `a`: average RX restart cost in us.
- `m`: max RX restart cost in us.

Expected baseline:

```text
h ~= 7900+
c = tens to low hundreds per 5s
t = low single digits
a ~= 3 us
m ~= 4 us, occasional higher spike acceptable
```

## Baseline Interpretation

When judging future changes:

- If `peek_hz` is around `8000` and `peek miss` is near `0`, SPI-to-TX handoff is healthy.
- If STM32 `txLen` is `16` and `input_hz` is about `7920`, STM32 is producing the expected 8K 12B input stream.
- If TX `irq/sent/upd_hz` is around `8000`, the TX trigger cadence is healthy.
- If RX `h` drops while `peek_hz` remains good, the issue is likely RF timing/air-link/RX restart, not STM32 SPI bandwidth.
- If RX `c` rises sharply after adding work inside `TMR0_IRQHandler()`, suspect high-rate ISR cost.
- If `sf/pf/rb` becomes nonzero, RFIP start/parameter scheduling is failing and sequence continuity is no longer guaranteed.

## Current Non-Goals

This baseline intentionally does not include:

- Frequency hopping
- Pairing/binding
- 15B gamepad payload
- SPI checksum validation inside the 8K hot path
- Full SPI command parser as the 8K data path
- RX decoding into final USB/XInput output

Those features can be reintroduced later, but each should be validated against this baseline first.
