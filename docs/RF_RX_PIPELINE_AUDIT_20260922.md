# RX 125us 处理能力审查

本轮按用户要求先审查 RX 全路径和时间证据，不继续用相同按键去重代替处理能力验证。审查对象为当前 RX 源码（含未提交 v29 修改），实测证据来自此前已有的 RX `0x1927` 日志。没有新开设备采集、运行回归、烧录或新增固件修改。

## 结论

当前实现是中断生产最新输入、主循环消费并再次合并、主循环提交 USB 的结构。它不是已经验证的“每 125us 接纳一份变化输入”的流水线。v29 修复了相同状态包导致提交失效的问题，但每包状态都变化时仍会触发版本失效；不能凭 v29 宣称满足 8K 处理要求。

现有证据不足以量出每阶段的完整执行耗时，也不能证明位映射运算本身超过 125us。可以确定的是：接收吞吐、主循环接纳吞吐、USB 完成吞吐是不同指标，原先的监测没有覆盖最后两项的完整性能条件。

## 实际执行路径

```text
RF 硬件接收 / SDK 中断入口（现有计时未覆盖全部入口延迟）
  → RF_ProcessCallBack：保存 RX 时间、取 RSSI、重新开启接收
  → demo_fast_rx_packet / demo_note_air_packet：协议/序号/统计/频道状态/ACK
  → demo_queue_rx_pending_packet：覆盖 g_channel_latest
                         ↓ 等待主循环
  → demo_process_pending_rx_packets：每次入口取一次 latest 快照
  → short_rx_edge + 短输入转换 + generation/状态修订检查
  → demo_queue_input_payload：去重，未处理的旧输入可被清掉
  → demo_process_pending_input_payload：构造 20 字节 XInput，覆盖 prepared
  → demo_service_xinput_report：端点空闲才提交
                         ↓ 等待 USB 主机 IN
  → USB2_DEVICE_IRQHandler：记录完成、清 busy、设 NAK
                         ↓ 下一份仍等待主循环提交
```

对应代码：`RF_PHY.c` 的 `demo_queue_rx_pending_packet`、`demo_queue_input_payload`、`demo_process_pending_input_payload`、`demo_service_xinput_report`、`demo_process_pending_rx_packets`、`RF_Service`；`RF_main.c:Main_Circulation`；`ch585_usbhs_device.c` 的 `DEF_UEP2` IN 完成分支。

三个交接点都可能合并：

1. ISR 覆盖 `g_channel_latest`，即使主循环尚未取走。
2. 名为 32 槽的 `g_demo_input_fifo` 在入队时发现未消费项，直接令 tail=head，再存新项。因此其当前策略不提供 32 份有序输入缓冲。
3. `g_demo_xinput_pending` 已置位时，构包仍覆盖待提交报告。USB 已在传输的缓冲不因此被改写，但尚未提交的中间状态会消失。

如果每 125us 都有不同状态，这些合并点可能删除真实状态。反之，同状态包合并本身未必造成按键丢失；必须分别计数。

## 已有日志的实际数字

同一组 150 条按键，事件时间 Unix ms `1790081927776..1790082029541`。以下累计计数按各自相邻诊断页的首尾差计算；各页相位不同，不应相减得到精确包守恒关系。

| 指标 | 区间 / 计算 | 结果 |
|---|---|---|
| RF 合法短 DATA 接收 | 1790081926197..1790082030202；802830 / 104.005s | 约 7719/s |
| 主循环短输入成功接纳 | 1790081926697..1790082030702；150498 / 104.005s | 约 1447/s |
| 软件合并总次数 | 1790081926951..1790082030463；627920 / 103.512s | 约 6066/s |
| 有 RX 时长的按键 | 149 条 | 最小 116us，中位 738us，最大 2987us |
| RX 小于 125us / 大于 250us | 同上 | 12 条 / 101 条 |

`g_demo_short_decoded` 在成功调用 `demo_queue_input_payload` 后递增，同状态去重返回也会计数，因此 1447/s 并不是“只数按键变化”的频率。它也不是 USB 完成频率，更不是 CPU 处理能力的理论上限：当前调度、序号检查与覆盖策略都会影响它。

`g_channel_coalesced` 混合了以上三个交接点，且不区分相同状态与不同状态。它能证明存在大量合并，不能直接换算为丢失按键数。

按键延迟采样不是每包基准测试。149 条事件的延迟分布不能单独推导持续吞吐能力；高吞吐流水线也可能具有多个周期的端到端延迟。

## 现有时间统计没有覆盖什么

| 现有测量 | 日志值 | 实际边界 / 限制 |
|---|---:|---|
| RX rearm max | 15us | 回调计时起点至重新接收完成；未覆盖 SDK 入口前延迟 |
| RX callback max | 2634us | 合法包回调整段累计最大值；此前已出现，不区分普通/ACK/控制包，也不是整个 RF IRQ 的完整占用 |
| Input commit max | 6us | 解码后临界区，未包含前面的事件建档/解码/调度等待 |
| Input capture max | 6us | FIFO 抓取与 report 发布两段临界区共用最大值；中间构包未计入 |
| RX 列 | 116..2987us | 已记录事件的 RX 边界到 report-ready，包含等待、重试及中断打断，不能当纯 CPU 时间 |
| USB 列 | 按事件记录 | report-ready 到完成回调，混合端点等待、主循环提交等待、主机调度和完成 ISR 延迟 |

`g_demo_edge_drop` 只有声明和遥测读取，没有递增路径。它一直为零不能证明无边沿丢失。`airPendingDrop` 只覆盖独立 pending 队列满，并不覆盖 latest/prepared 合并。

## 调度上的风险点

- 普通输入每轮只抓取一次 latest，然后可处理最多 16 个 pending 项。辅助分片的 `continue` 跳过中间输入服务；这段处理期间新到的 latest 要等下次进入函数。这里有条数上限，没有 125us 对应的时间预算。
- `RF_Service` 在主循环中执行；每 625us 到期的 housekeeping 使用全局关中断区，包含无线状态处理和定时器调度。`TMR2_IRQHandler` 也在全局关中断下执行频道状态机。625us 是维护调用周期，不是证明其执行只需某个固定微秒数。
- RF 接收回调包含多项累计统计、时间查询及频道管理；重新开启接收快，不等于回调能很快返回给主循环。
- 主循环还串行执行 USB 遥测构包/事件扫描。`short_send_trace` 一次最多扫描 63 个槽位；独立 USB 端点避免了数据缓冲混用，但没有隔离 CPU 和主循环时间。
- EP2 单缓冲完成后只清 busy/NAK，没有立即接续已经准备好的下一份报告。下一次主循环晚到，可能错过后续主机取数机会。
- HS 配置的 EP2 interval 为 1 微帧，FS 回退为 1ms。固件允许 HS 协商不等于现有日志确认了实际协商结果；每 125us 交付不同 USB 状态的要求必须限定在实际 HS/主机持续轮询条件下。

这些是需测量的候选阻塞点；不能把调用次数、RAM 地址或静态指令条数直接换算成已经实测的执行时间。

## 正确的 125us 验收口径

需要分别回答三件事：

1. 普通稳态中，持续每 125us 到达一个不同输入，RX 能否接纳、处理并保留所需顺序，不靠覆盖来维持表面收包率？
2. 每份输入从接收至 report-ready 的响应时间上界是多少？是否允许固定多级延迟，应明确约定；吞吐 8K 不必等于每份端到端耗时小于 125us。
3. 在实际 HS 主机轮询下，USB 能否连续完成报告？RF/USB 时钟相位和短期抖动需要有界缓冲，不能无限积压。

RF DMA 和 USB DMA 可以与 CPU 重叠，但解码、中断、构包和维护共用一个 CPU。稳态 CPU 平均每包工作（RF ISR + 主循环处理 + USB ISR + 分摊维护）必须明显小于 125us，并且最长不可服务时间也要受到约束。仅证明每个函数分别小于 125us 不足以成立。平均满足预算也不能证明最坏延迟。

ACK/频道切换造成的真实无线静默应单独分类，不能混进纯普通 DATA 处理能力，又不能在最终端到端体验统计中隐藏。

## 下一步应补的测量，而不是先猜优化

使用设备上的周期计数器做低开销、有界统计，保持普通输入行为不变：

- 每包：RF 回调入口/重新接收完成/快照发布/回调退出。
- 每次消费：取快照/转换结束/构包结束/端点提交。
- 每次 USB：IN 完成/下一报告装载，记录实际 USB 速度。
- 全路径：主循环输入服务的最大间隔；各 ISR 的累计占用；最长关中断区；维护/辅助分片/遥测构包耗时。
- 分开计数：收到、被主循环取出、同状态合并、不同状态覆盖、版本检查拒绝、prepared 覆盖、USB 提交/完成、队列水位与溢出。每份已测样本必须带同一个输入身份，不能把不同包的时间拼起来。
- CPU 执行时间与包含抢占的经过时间分别解释，避免给主循环嵌套中断重复记账；计时读取与记录开销也要校准。

只在 RAM 累加计数/直方图并保留少量尖峰样本，低频发送摘要，不能每个包都发诊断或打印。按普通 5B、带辅助信息 7B、ACK/控制包分组；关闭/开启测量分别观察，防止测量功能本身改变结论。

最终负载需包含持续不同输入，而不只是按住某个键；同状态流用于对照。测量前后保持同样频道、速率和 USB 条件。本轮只记录测量设计，没有自动运行该负载。

根据结果再决定：缩短 ISR、把低优先级工作拆成有时间预算的小块、简化多级输入复制、采用明确所有权的有界缓冲、在 USB 完成后安全接续已准备报告。简单扩大 FIFO 会增加排队延迟；把所有工作搬进 RF ISR 又可能破坏重新接收/ACK/USB 的响应，均不应先于测量。
