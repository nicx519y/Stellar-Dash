# SPI 输入接收与测量调度修复 v14

本轮从代码分析修改 TX，已编译，未烧录、未采集设备、未运行回归测试。
实机验收由用户完成。本版本基于 v13；STM32、RX（0x1913）和 connect-monitor
沿用原版本。不能把构建成功当作闪键或源记录缺失已通过实机验收。

## 截图所表示的缺失

`Source record missing` 表示 RX 已有状态变化和本地阶段，但没有接受到对应的
STM32/TX 源记录候选。它不表示这行不是按键变化，也不表示 ADC/Logic/SPI 用时为零。
监视器仍保留真实状态变化和部分阶段，不删除不完整行、不补造总耗时。

Hitbox 当前优先读取 Windows XInput，未用遥测的“窗口内曾按下”掩码作为当前状态。
实体 LED 未闪不能单独证明 ADC 没有瞬态：LED 和 Windows 的刷新路径不同。
本轮没有按假设给前端加防抖，也没有把按键变化过滤掉。

## 代码缺陷及处理

1. TX 在附带通道空闲时，每轮扫描 63 个测量槽，逐槽关中断复制整个记录，
   然后才检查它是否为空、已发送或未收到源记录。SPI 消费也依赖同一主循环，
   因此测量无数据时仍占用处理预算。改为每轮最多检查 4 个槽，先检查资格，
   只有可发送记录才复制。游标持续轮转，输入处理不会等待一整轮诊断扫描。
2. SPI DMA 的 1024 字节环只保存模 1024 的读位置，原代码将 DMA_END 清除后
   丢失圈数，不能在位置不同的情况下识别生产者已超过消费者一整圈。
   在积压场景下可能把覆盖后的字节接到旧的半帧后面；直接读活动 DMA 缓冲
   还会让解析时的数据被后续传输改写。
   现在用 DMA_END 的短中断维护绝对生产位置，以无符号差计算剩余量；位置
   快照同时处理尚未执行的中断。每次先复制最多 64 字节，再复核没有被覆盖，
   才交给解析器。每次服务最多消费 256 字节。检测覆盖则丢弃不可信区间并
   重置半帧解析，不把旧缓冲作为新输入重放。丢弃计入现有 backlog 计数。
3. STM32 输入已有 CRC8（多项式 0x07），TX 接收路径却只检查 SPI 外层累加和。
   外层累加和不能充分识别拼接或字节抵消错误。现先验证输入 CRC8，再更新
   序号基线、按键快照和测量事件。采用半字节查表，不增加协议字节或空口发送。
4. FIFO 溢出标志交由主循环复位接收流；RX DMA 中断不提前清掉这个错误，
   避免解析器将溢出两侧的字节当作连续数据。SPI 回包仍用 v13 的 CNT_END
   恢复接收，RX 的 DMA_END 圈数和 TX 的发送完成分开处理。

错误输入被发布后，后续正常输入可能马上将其改回，从而产生很短的按下/释放；
错误或旧事件 tag 也会使源记录关联失败。以上是代码中存在的风险路径，
本轮没有硬件证据证明它们贡献了截图中多少条缺失或全部闪键。
源记录仍采用有限分片重传，空口丢片、源输入首帧丢失等情况仍可能产生部分记录。

## 交付与更新

目录 `.hbox/rf-latency-v14-20260920/`：

- `TX.bin`：现有 TX 烧录工具使用的镜像格式。
- `TX_app.bin`：同次构建的 Application 镜像。
- `SHA256SUMS.txt` / `manifest.json`：校验值和构建状态。

本轮仅需更新 TX。使用原入口 `python tools/hbox.py flash tx`，该命令使用仓库
当前构建产物；不要改成从零地址手动刷整片。目录中的 TX.bin 包含现有 IAP 前缀，
它不是授权覆盖 0x0000–0x0FFF 的指令。原流程只更新 0x1000 以上 Application。
STM32 保留 v13，RX 保留 0x1913；如果此前没有更新 v13，应先按 v13 配套说明完成。

没有修改烧录脚本、IAP 布局、保护位或锁定状态。构建保留既有未使用符号及
链接 RWX 段警告，未宣称无警告构建。
