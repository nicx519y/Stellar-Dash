# XORA RF 控制链路恢复修复

## 故障依据

`b1a9d6d1`（2026-09-29）首次引入 RF W_INT 释放超时锁存，并在发送入口检查该状态。运行期保护继续保留；不能仅凭引脚后来变高就清除协议故障。

只读 ST-LINK 记录 `.hbox/rf-stlink-confirm-20261005-090908/decoded.json` 显示 RF 释放超时 80 ms、发送计数停滞、STM32 确认 8000 Hz 而最后收到的 TX 状态为 0 Hz。记录确认了锁死和确认状态失配，没有捕获最初触发故障的波形，不能据此断言唯一触发原因。

## 实现

- 普通冷启动复用 `RfSleepRecovery` 的异步应用交接：已有 ROLE_SELECTED 不重复重启；至少等待 150 ms，且 W_INT 已释放，才交接 USB 角色选择端口与 RF 端口。持续低电平在 500 ms 后进入失败路径，不将启动提示当回复读取。
- SET_RATE 的本地 DMA 完成不再合成 RATE_APPLIED 或覆盖 TX 速率。冷启动、恢复及运行期改速率均要求新的物理 GET_STATUS 确认；保留一次 1 kHz 降级。
- 普通运行出现锁存释放故障、连续三次状态查询失败/无回复或已确认速率与新状态不一致时，停止普通 RF 生产者，检查 SPI/DMA 已停，再通过现有角色启动流程重启 TX。RX 离线本身不触发重启。
- 冷启动与每次运行期恢复最多三次尝试，重试间隔沿用 10 秒；次数耗尽后保持无线输出停止，等待用户重新切换物理模式。本地输入采样和屏幕继续工作。检查停 SPI 失败时保留 TX 供电，不强行断电。
- 速率确认和中立帧发送完成后恢复无线输入；恢复期间保留本地采样时钟，冷启动暂用 1 kHz。模式切换、退出输入状态和传输清理取消后台恢复。
- 原休眠恢复调用保留原有重试策略。未修改共享握手锁存策略、空口协议、绑定、固定频道、TX/RX、烧录流程或深度 Standby 限制。

## 11:49 短暂连接后断开

用户手动切换模式或拔插后复现两次短暂连接。已有监视器日志显示首次 11:49:21.755 进入 Connected，11:49:24.370 转 Reconnecting；连接期间 RX DATA 约 7.7–7.9 kHz。11:49:45 的再次连接是手动操作后的结果，不能记为自动恢复成功。

只读 ST-LINK 记录 `.hbox/rf-disconnect-20261005-115104/`：设备的连接管理和恢复代码片段与 11:47 的 Application ELF 一致；状态查询连续失败计数为 3，恢复到达 Failed，已尝试 3 次，最后恢复错误为 Role。端口累计控制 DMA 完成 14 次、发送错误 0、无效接收帧 1；连接管理最后观察到的物理状态代次为 10。最后的握手故障属于角色选择端口（USB owner、20 ms），是恢复过程中记录的，不能代替最初断连原因。未停止/复位 CPU，未写硬件或访问保护配置；普通缓存 RAM 的读取仍有缓存滞后限制。

发现上一版遗漏：异步 GET_STATUS 发出后，普通输入继续发送；TX 回复需要在 SPI RX/TX 之间切换，输入可能抢先消耗回复，或持续占用 RX 阻止回复发送。仅有成功发送和未收到回复不能区分这类竞争与 TX 真正失联。

修正：状态查询只在端口空闲时发出；发出后普通输入暂停，事件接收继续，收到新物理状态立即解除，最迟 20 ms 超时解除。端口繁忙/新事件抢占只推迟查询，不消耗失败预算。500 ms 查询周期及三次失败后的有界恢复保留；不以扩大重试次数掩盖问题。

新增 `g_rfRuntimeRecoveryDiagnostic` 保存首次恢复前的原因、速率、状态代次和输入计数；`g_rfRoleReplyDiagnostic` 保存首次无效角色回复的原始字节和 HAL 结果，均在清理会话后保留并清理 D-cache。后者是诊断补充，角色选择失败的具体触发条件尚未捕获，未宣称已修复该触发源。

新增生产函数场景检查查询期间输入门控、收到回复后恢复、20 ms 超时解除以及繁忙不计失败，已编译未执行。STM32 无锁增量编译通过（约 8 秒）；差异检查通过。保持 RF 自动回归暂停，未烧录第二版；仍需用户实机验证稳定连接。
