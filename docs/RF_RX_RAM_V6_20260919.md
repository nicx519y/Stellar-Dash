# RX v6：缩短接收重启与输入临界区的执行路径

## 交付

仅烧录 `.hbox/rf-rx-ram-v6-20260919/RX.hex`，沿用已验收的 RX 普通烧录方法。
RX.bin 是同一镜像的替代格式，不需要两份都烧。TX、STM32 不更新。
诊断 build ID 为 `0x1906`；固定配对、8K、频道 39、关闭自动跳频。
SHA-256 见同目录 `SHA256SUMS.txt` 和 `manifest.json`。

## 定位依据与修改

v5 新采样 30 秒，记录 228719 / 242560 个有效/期望包，目标缺额 5.71%，无重连或跳频。
此前一分钟 v5 采样的软件原始包队列丢弃为零，但接收率仍约 7541 Hz。
这说明软件队列改善没有消除剩余 RF 接收缺额。

检查链接产物发现，RF 回调入口虽然在 RAM，接收重启和输入处理函数仍位于 Flash。
v5 的输入提交/消费临界区启动后最大值分别为 24/31 us；这些最大值不等于平均值或 P95。
本轮针对可观察的执行开销做单变量接收端对照，不宣称它已被证明是全部 5.7% 缺额的原因。

- 将接收重启、原始包队列入队/出队、短包提交、输入构包/发布及 USB 输入消费函数放进 `.highcode` RAM 段。
- 一并移动正常短包路径的 RSSI、计时、遥测开关、字段读取等小函数。检查最终机器码，避免函数入口在 RAM、内部仍跳回 Flash 的情况。
- 原始包和输入临界区使用 RAM 字节复制/清零函数，兼容非对齐的 10/20/32 字节存储；通过 volatile 字节写入阻止编译器重新替换为 Flash libc 调用。按键比较保留四个字节的完整语义。
- RSSI 硬件值仍在重启接收之前读取；总和、计数及极值更新放在接收重启之后，减少重新监听前的工作。
- 不调整空口包长、ACK 参数、TX 发送保护、重连阈值、队列深度、USB 顺序、中立输入保护或 IRQ 优先级。RHD1 布局和指标含义不变。

## 验证

31 项主机行为/契约测试通过，包括 RAM 复制与清零的全部 0–32 字节长度、四种源/目标对齐和前后边界；原有按键组合、USB 忙时顺序、代次及中立复位测试仍通过。
固定配对与正常配对 RX 构建均通过。
已检查 ELF：关键函数位于 `0x2000...` RAM；原始包出队、短包提交、输入队列写入、输入快照/提交的直接调用均未跳入 Flash。
USB 消费中的非临界区延迟计算、控制/配对路径仍可调用 Flash；没有把整个 SDK 搬到 RAM。
RAM 总占用 31948 字节（31.2 KiB，128 KiB 的 24.37%），较 v5 增加 2360 字节；Flash 占用 49656 字节。

## 烧录后对照

先确认 `rfBuildId=6406`，保持固定频道 39、8K、相同 USB 接口与设备位置。
采集至少 60 秒并比较接收率/目标缺额、CRC、序号缺口、软件丢弃、接收重启及输入临界区耗时。
期望软件丢弃继续为零，同时观察临界区缩短是否转化为有效接收增加。
若耗时下降而接收缺额不降，应进一步在 TX 增加 SDK 返回失败、未归属完成回调和实际发起间隔诊断；不可直接缩短发送保护或把缺额都归因于无线环境。

TX 现有 started 计数位于 SDK 调用之前，只代表启动尝试；短 DATA 的 TX_FINISH 被现有所有权过滤忽略，不能把当前 tx_finish 当作全部短包发送成功数。本轮已核对代码，未更改这套统计或对外宣称实际成功发送数。

此包交付时尚未实测，不是已验收稳定版本。用户后续已烧录并确认 0x1906：临界区降到 5/7 us，软件丢弃为零，但频道 39 首轮一分钟目标缺额仍为 7.63%。七频道对照与策略审查见 [RF_HOP_AUDIT_20260919.md](RF_HOP_AUDIT_20260919.md)。本轮未执行烧录，未修改保护位、锁定状态或冻结烧录流程。
