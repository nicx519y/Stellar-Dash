# connect-monitor 主线程卡顿修复（2026-09-22）

本次只改 PC 监视器，不更新 STM32/TX/RX，不启动设备采集、回归测试或烧录。

## 代码中确定的问题

- `MonitorEventBus` 的 500 条内存缓冲满后，每个新事件都会驱逐一条历史；原来的 `append()` 每次都在 Electron 主线程执行 `appendFileSync()`。持续遥测因此变成逐条同步磁盘写入。历史翻页的同步读盘/JSON 解析也占用同一线程。
- `node-hid` 的枚举、打开、SET_REPORT、GET_REPORT、关闭均使用同步 API。配置回执每秒查询一次，原来会阻塞 Electron 主线程、其他 IPC 和 Hitbox 的原生按键查询。
- renderer worker 原来发送完整快照。结构化克隆让未变化的曲线数组也获得新引用，触发重复整理数据及 ECharts `setOption()`。收到快照时还在 React 提交前就释放了下一次快照的额度。
- 每 30 秒运行的内部诊断日志也使用同步磁盘操作。

这些是静态代码确认的阻塞/重复工作路径；未采集性能时间线，不能断言某个路径占本机卡顿的百分比，也没有实测帧率结论。快速实验面板仅在打开弹层时挂载，不能把关闭面板时的所有卡顿归因于它。

## 修改

- 新增 HID worker/client，现有解析、控制回执、延迟续期及 RF 恢复后重发配置逻辑在 worker 内继续执行。Electron 主线程读缓存状态，不做 HID 控制调用。
- HID 数据以最多一批在途的方式传递；待发队列最多 4000 条，每批最多 500 条。配置变化只保留最新待发值；实验控制最多 8 个未完成请求，排队过期不执行。回复超时表示设备状态未确认，不宣称操作未发生。
- 暂停/恢复等待旧 HID worker 关闭，不同时打开两个 reader。worker 异常报告断开，用户暂停/恢复可重建；不自动重新开启快速实验。
- 历史存储使用独立 worker，50ms 合批。最多 5000 条待存事件、一个在途任务及 8 个历史查询；慢磁盘不阻塞输入显示。归档溢出计数、HID 队列溢出及写入错误进入原有内部诊断日志，不伪装成 RF 丢包。
- 清空历史使用代次隔离，旧查询结果不能重新填入界面。正常退出异步等待清理，等待期限有界。
- renderer worker 仅发送改变的快照部分，未改变的曲线保留引用；React 提交后才允许下一份快照。图表的统计窗口、数据值、样本保留数量不变。
- 普通内部诊断日志改为异步写入；仅进程致命异常保留同步应急记录。
- 实验面板的三次复制/倒序查找改为一次反向遍历。

## 使用与交付

关闭原监视器，再从 `connect-monitor` 执行 `npm start` 使用新的本地 `dist` 构建。若使用另一目录的安装版，须使用更新后的监视器资源，重开旧安装包不会加载本仓库的新代码。

无需烧录固件。软件类型检查和构建可以确认产物生成，实际流畅度、暂停/恢复、重新连接及延迟开关行为由用户验证。没有改变 RF 统计口径或降低图表数据采样率来隐藏波动。

本次 `npm run typecheck`、`npm run build` 已通过；Vite 提示主 bundle 较大，这是构建警告，不是本次测得的运行时瓶颈。未启动监视器或自动执行测试。可更新的 `dist` 资源归档在 `.hbox/monitor-ui-threads-20260922/monitor-dist.zip`（仓库根目录下），附 SHA-256。
